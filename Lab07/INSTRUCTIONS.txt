Lab 07 - Single-Cycle Processor
===============================

Run these commands from the Lab07 directory in a Linux/WSL terminal with
Icarus Verilog (iverilog and vvp) and GTKWave installed. Commands from earlier
OpenCode chats were not available in this workspace; these follow the local
Lab05 convention of running compiled test programs from the terminal.
If this Windows network-share folder is not visible inside WSL, copy the Lab07
folder to the WSL filesystem or use the Linux mount path for the share first.

1. Test the control unit
-----------------------
Compile and run the self-checking tests. The test covers every don't-care
opcode combination for the supported instruction patterns, including ADDI
and MOVZ, and checks unmatched opcodes return default controls.

    iverilog -g2012 -s SingleCycleControlTest -o control_test.vvp SingleCycleControl.v SingleCycleControlTest.v
    vvp control_test.vvp
    gtkwave singlecyclecontrol.vcd

The terminal should report "All control-unit tests passed". In GTKWave, inspect
the opcode and control-signal transitions. Close GTKWave before running the
processor test if you prefer a separate waveform window.

2. Test the complete processor
-----------------------------
Compile all modules used by the top-level processor and its testbench:

    iverilog -g2012 -s SingleCycleProcTest_v -o processor_test.vvp ALU.v DataMemory.v InstructionMemory.v NextPClogic.v RegisterFile.v SignExtender.v SingleCycleControl.v SingleCycleProc.v SingleCycleProcTest.v
    vvp processor_test.vvp
    gtkwave singlecycle.vcd

Both programs must pass. Program 1 checks the original instruction set and
must complete with result 0xF. Program 2 runs after Program 1 and must report
"MOVZ/store/load Program 2 passed" with result 0x123456789abcdef0. It builds
that value from four MOVZ instructions, combines the pieces with ORR, stores
the result at byte address 0x28, and loads it into X10.

3. Lab/demo checklist
---------------------
- Explain the control-unit defaults and opcode-to-control mappings, including
  why an unsupported opcode does not write a register or memory.
- Explain the top-level datapath connections, MOVZ shifted-immediate path, and
  how the testbench checks both programs.
- Show the passing terminal output and the VCD signals in GTKWave.
- Keep the original Program 1 before Program 2 in the testbench; it verifies
  the extension did not regress the original processor.
- For the written MOVZ response, include the control signals and describe how
  the immediate is shifted by 0, 16, 32, or 48 bits before ORR combines it.

The hand-encoded Program 2 assembly is:

    MOVZ X9,  0x1234, LSL #48
    MOVZ X10, 0x5678, LSL #32
    MOVZ X11, 0x9abc, LSL #16
    MOVZ X12, 0xdef0
    ORR  X9, X9, X10
    ORR  X9, X9, X11
    ORR  X9, X9, X12
    STUR X9, [XZR, #0x28]
    LDUR X10, [XZR, #0x28]

Implementation notes for the Lab 7 questions
=============================================

1. Control unit: `SC_Control` decodes the supported opcodes with `casez` and
   initializes every control output to zero before decoding. Thus an unsupported
   or garbled opcode performs no register or memory write and selects no branch.
   The testbench covers the opcode don't-care combinations and samples ten
   random unsupported opcodes. The main limitation of this strategy is that
   random testing does not exhaustively cover all 2,048 possible opcodes; the
   supported patterns are exhaustively tested over their don't-care bits.

2. Processor: `SingleCycleProc.v` connects the instruction memory, control,
   register file, sign extender, ALU, data memory, and next-PC logic. The
   existing processor testbench preserves Program 1 before starting the
   MOVZ/store/load Program 2. Neither testbench has been run yet, so there is
   no simulator output or GTKWave demo to report here.

3. MOVZ extension: MOVZ writes a zero-extended 16-bit immediate shifted by
   0, 16, 32, or 48 bits into the destination register. The control unit
   selects ALU pass-B and enables register writing. The top level detects
   MOVZ and supplies the shifted immediate directly to the ALU; the normal
   ALU pass-B operation then writes it through the existing register-file
   writeback path. No new control signal is required.

   | Instruction | Reg2Loc | ALUSrc | MemtoReg | RegWrite | MemRead | MemWrite | Branch | Uncondbranch | ALUOp | SignOp |
   |---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
   | MOVZ | 0 | 1 | 0 | 1 | 0 | 0 | 0 | 0 | 0111 (PassB) | 00 (unused) |

   The test program builds `0x123456789abcdef0` in X9 using four MOVZ
   instructions and three ORRs, stores it to byte address `0x28`, and loads it
   into X10. The corresponding machine-code program is already in
   `InstructionMemory.v` at addresses `0x34` through `0x54`. The top-level
   testbench starts this program after Program 1 and checks the loaded value.

   Lab 7 implementation files: `SingleCycleControl.v`,
   `SingleCycleControlTest.v`, `SingleCycleProc.v`, `SingleCycleProcTest.v`,
   `ALU.v`, `NextPClogic.v`, `SignExtender.v`, and `RegisterFile.v` in this
   directory. `InstructionMemory.v` already contains the MOVZ/store/load
   program. The code changes are present, but simulation and the required
   GTKWave demonstration remain to be completed.

MOVZ implementation explanation
--------------------------------

MOVZ's opcode is recognized by the `110100101??` pattern in
`SingleCycleControl.v`. Its control settings enable register writes, select the
immediate operand, and set `ALUOp` to `0111` (PassB). The memory, branch, and
other write controls remain zero. `SignOp` is unused for MOVZ because the
top-level MOVZ path does not use the sign extender.

In `SingleCycleProc.v`, `isMovz` detects the MOVZ opcode. The immediate is
zero-extended from instruction bits `[20:5]` and shifted left by 0, 16, 32, or
48 bits according to shift field `[22:21]`. The `aluInputB` mux gives this
MOVZ value priority over the normal register/immediate inputs. The ALU's
PassB operation forwards it to `aluout`, and the existing writeback mux selects
the ALU result and writes it to destination register `rd` because `RegWrite`
is asserted. No new ALU operation, sign-extension mode, or writeback path was
needed.

A MOVZ writes its immediate and clears the other bits of its destination, so
the test constructs the 64-bit constant in four separate registers, with one
16-bit chunk per MOVZ. Three ORR instructions combine those chunks into X9;
STUR writes X9 to byte address `0x28`, and LDUR reads it into X10. The relevant
code to walk through or copy for the MOVZ change is the MOVZ decode in
`SingleCycleControl.v`, the MOVZ detection/immediate/ALU-input mux in
`SingleCycleProc.v`, and the test program in `InstructionMemory.v` plus its
second-program checks in `SingleCycleProcTest.v`.
